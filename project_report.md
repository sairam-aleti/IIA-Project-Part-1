# Project Report: Ministry of Transportation GAV Mediator System

> **Course**: CSE656 Information Integration & Application  
> **Topic**: Uninsured/Flagged Vehicle Identification System  
> **Architecture**: Global-As-View (GAV) Federated Data Mediator

---

## 1. Problem Statement & Motivation

The Ministry of Transportation (MoT) relies on multiple autonomous and geographically distributed data sources to monitor vehicle compliance. However, this data exists in **heterogeneous silos**:
- **RTO Database**: Stores vehicle registration and ownership. Primary Key: `reg_num`.
- **Insurance Database**: Stores active/expired insurance policies. Primary Key: `vehicle_reg_no`.
- **Police Database**: Stores stolen and scrapped vehicle records. Primary Key: `license_tag`.
- **Camera Network**: Captures live traffic sightings via ANPR. Primary Key: `plate_id`.

### The Challenge
To identify an uninsured or stolen vehicle that is actively driving on the roads, an officer previously had to manually query four different databases, each with completely different table structures, column names, and data formats. There was no single source of truth.

---

## 2. The Solution: Global-As-View (GAV) Mediator

This project implements a **Federated Data Mediator System** using the **Global-As-View (GAV)** approach. 

Instead of copying millions of records into a centralized, redundant data warehouse (the ETL approach), the Mediator provides a **virtual global schema**. When a user requests data, the mediator translates the global query into local sub-queries, dispatches them to the autonomous databases in real-time, and merges the results on the fly in memory.

### Key Benefits of this Architecture
- **Zero Data Duplication**: The mediator stores no vehicle data; it fetches it live, saving massive amounts of storage.
- **Real-Time Accuracy**: If a car's insurance expires at 11:59 PM, the mediator reflects this at 12:00 AM immediately. A data warehouse would be delayed until the next batch sync.
- **Extensibility**: Adding a 5th database (e.g., Emission Testing) simply requires writing a new Wrapper, without altering the existing global schema.

## 3. Technology Stack

- **Backend / Mediator Engine**: Python 3.13, FastAPI (Asynchronous API)
- **Database Simulation**: SQLite3 (4 isolated `.db` files representing distributed servers), SQLAlchemy Core

## 4. Under the Hood: Deep Dive into Query Unfolding (How Data is Fetched)

The defining feature of this project is how a single API request from the frontend is "unfolded" into four distinct SQL queries. Here is the exact step-by-step internal execution trace when an officer searches for plate `REACT123`.

### Step A: The API Request
The React frontend makes a `GET /api/v1/vehicle/REACT123` HTTP request to FastAPI. FastAPI receives this and passes it to the `GAVMediator` class.

### Step B: The View Unfolding (Dispatch)
Inside `mediator.py`, the `query_vehicle(plate)` method is triggered. The mediator holds references to four "Wrappers" (one for each database). It loops through these wrappers and calls `wrapper.query('REACT123')` on all of them.

### Step C: Local SQL Translation inside the Wrappers
Each Wrapper is an isolated bridge to a specific SQLite file. Crucially, the Wrapper *does not hardcode the column names*. It uses the configuration generated by the AI schema matcher (explained in Section 5). 

For example, when the `PoliceWrapper` is called:
1. It looks up its mapped local key (e.g., `license_tag`).
2. It dynamically builds an SQLAlchemy text query: `SELECT * FROM StolenRecord WHERE license_tag = 'REACT123'`
3. It opens an isolated connection to `police.db`, executes the query, and fetches the row.

### Step D: Normalization & Conflict Resolution
Before returning data to the Mediator, the Wrapper normalizes it:
- **Type Casting**: SQLite stores booleans as `0` or `1`. The Police wrapper converts this to Python `True/False`.
- **Semantic Conflict Resolution**: The `InsuranceWrapper` fetches the policy. However, even if the database string says `status = 'Active'`, the wrapper mathematically checks `expiry_date < today()`. If true, it overwrites the status, dynamically deriving `is_insured = False`.

### Step E: Global Join & Presentation
The Mediator collects the four normalized JSON responses. It performs an in-memory merge, constructing a single massive `MoT_Report` dictionary. 
- It pulls `owner` from the RTO response.
- It pulls `is_stolen` from the Police response.
- It pulls `last_seen` from the Camera response.

Finally, it calculates aggregate "Flags" (e.g., `['UNINSURED', 'STOLEN']`) for the UI badge system and returns the payload to React.

## 5. Under the Hood: AI-Driven Schema Matching

In a real-world federation, database schemas change. Hardcoding `SELECT * FROM Vehicle WHERE reg_num = ?` breaks if the DBA renames `reg_num` to `plate_number`. 

This project solves this by running an **Algorithmic Schema Matcher** every time the server boots (`schema_matcher.py`).

1. **Target Definition**: We define a global concept string: *"vehicle identifier registration license plate number"*.
2. **Reflection**: SQLAlchemy inspects the metadata of all 4 SQLite databases to extract all table and column names dynamically.
3. **NLP Embeddings**: We pass the global concept and all local column names through the `all-MiniLM-L6-v2` transformer model to convert the text into dense mathematical vectors (embeddings).
4. **Scoring Function**:
   - *Semantic Score* (60% weight): Cosine similarity between the vectors. This allows the AI to realize that `license_tag` means the same thing as `plate_id` even though they share no letters.
   - *Syntactic Score* (40% weight): Levenshtein distance ratio. This catches exact string matches or slight typos (e.g., `reg_num` vs `regnum`).
5. **Mapping Generation**: The column in each database with the highest combined score is selected as the local Join Key and passed to the Wrappers.

## 6. Full CRUD Implementation

The mediator doesn't just read data; it can write it. When an officer creates a new vehicle via the UI (`POST /api/v1/vehicle`):
1. The Mediator receives the massive JSON payload.
2. It calls `insert()` on all four Wrappers simultaneously.
3. The RTO wrapper translates its portion into an `INSERT INTO Vehicle (reg_num, owner_name...)` SQL query.
4. The Insurance wrapper translates its portion into `INSERT INTO Policy (vehicle_reg_no, insurer_name...)`.
5. Only if all local database transactions commit successfully does the Mediator return a success response. (Deletions and Updates follow the same distributed transaction pattern).

## 7. Data Provenance

In government and law enforcement IT, **auditability is mandatory**. If the UI says a car is "Stolen," the officer must know exactly *where* that fact came from.

To achieve this, every Wrapper injects a `provenance` dictionary into its response. For every piece of data, it logs:
1. `source`: Which database provided this? (e.g., `police.db`)
2. `table`: Which table? (e.g., `StolenRecord`)
3. `local_column`: What was the exact column name? (e.g., `is_stolen`)
4. `retrieved_at`: The exact ISO-8601 millisecond the query was executed.
5. `derivation`: If logic was applied (e.g., `expiry_date < today()`), the logic is logged.

The Mediator merges all these traces into a master `provenance` object, which is viewable in the React UI by clicking "Show Data Provenance Trace".

## 8. Viva Preparation: Anticipated Questions & Answers

**Q: Why use a Mediator (Virtual Integration) instead of a Data Warehouse (ETL)?**
> A Data Warehouse requires copying all data into a central repository. This introduces latency. If a car's insurance expires at midnight, the warehouse won't know until the next ETL batch job runs. A Mediator queries the live operational databases directly, guaranteeing that the Ministry of Transportation sees real-time, up-to-the-second data. It also avoids storing massive amounts of redundant data.

**Q: Explain how your schema matcher works. Why not just use regex?**
> Regex only catches syntactic patterns. It wouldn't know that `license_tag` and `plate_id` represent the same concept. By using HuggingFace sentence-transformers, the system maps words into semantic vectors. It understands the *meaning* of the column names, allowing it to dynamically link schemas even if the DBAs use entirely different vocabulary.

**Q: How is the GAV mapping represented internally?**
> The global schema is the `MoT_Report` JSON object. The mapping is represented as a dictionary generated at startup that maps the global concept "vehicle identifier" to local tuples like `(camera_db, Capture, plate_id)` and `(police_db, StolenRecord, license_tag)`. The wrappers use this mapping dictionary to dynamically construct their SQL queries.

**Q: What happens if one of the autonomous databases goes offline?**
> The Mediator uses a fault-tolerant architecture with `try-except` blocks. If the Camera database crashes, the `wrapper.query()` fails safely and returns `None`. The Mediator still merges the RTO, Insurance, and Police data, simply leaving the `last_seen` object empty. The system degrades gracefully rather than crashing entirely.
